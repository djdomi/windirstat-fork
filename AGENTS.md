# windirstat-fork Repository Governance
# **Repository**:[ https://github.com/wiki-mod/lancache-ng](https://github.com/djdomi/windirstat-fork)
This file contains the repository-wide rulebook and MUST apply to all repository paths and all repository work.

## AG-LAW
* **[AG-LAW-001]** `AGENTS.md` MUST be treated as one unified rulebook. All applicable rules MUST apply simultaneously to every affected part of the project and to the change as a whole. Compliance with one applicable rule MUST NOT establish overall compliance. Every touched file, asset, generated output, behavior, or other affected part of the project MUST be checked against every applicable rule. A task MUST NOT be declared complete until the complete affected change has passed this audit. Partial verification followed by a completion claim MUST itself violate this rule.
* **[AG-LAW-002]** Every time stated in maintainer-visible communication under `[AG-CC-002]` MUST use Berlin local time (`Europe/Berlin`) and MUST include the seasonally correct `CEST` or `CET` abbreviation immediately after the time. Fixed UTC offsets MUST NOT substitute for `Europe/Berlin`. External times MUST be converted before being stated and MUST be verified against an independent authoritative source rather than relying only on session environment, local `TZ`, or tool defaults. Raw machine output and non-visible internal reasoning MAY be exempt.
* **[AG-LAW-003]** Every binding requirement or prohibition in this rulebook MUST use RFC 2119 terminology. Binding requirements MUST use `MUST`, `REQUIRED`, or `SHALL`; binding prohibitions MUST use `MUST NOT` or `SHALL NOT`. `SHOULD`, `SHOULD NOT`, and `MAY` MUST be used only for genuine recommendations or optional behavior. Bare imperatives, ambiguous equivalents, or negated `MAY` constructions MUST NOT replace the applicable RFC 2119 keyword.
* **[AG-LAW-004]** Every rule reference MUST use the stable rule identifier in the form `[AG-XX-XXX]`. `AGENTS.md` line numbers MUST NOT be used or treated as authoritative rule references. This requirement MUST apply to humans, agents, AI systems, bots, automated reviewers, tools, and integrations.

## AG-CC
* **[AG-CC-001]** Maintainer-facing chat and session communication, including visible reasoning or thinking presented to the maintainer, MUST be in German. Content that is or becomes GitHub-visible MUST instead follow `[AG-GH-001]`.
* **[AG-CC-002]** `[AG-CC-002]` MUST apply recursively to every dispatched agent and every further spawn level. Dispatch prompts and reports returned to a dispatcher MUST use German instructional prose. Literal code, logs, commands, paths, commit messages, and GitHub-bound content MUST remain in their required original or English form. Every spawning agent MUST propagate this rule.

## AG-DOC
* **[AG-DOC-001]** Current executable checks and verified code behavior MUST be treated as ground truth. Documentation MUST NOT contradict behavior verifiably enforced by code or CI and MUST be treated as stale when it does.
* **[AG-DOC-002]** `AGENTS.md` MUST define repository-wide hard rules for agent behavior, workflow, validation, and governance. Rules MUST be sober, direct requirements, prohibitions, permissions, or conditions and MUST NOT contain storytelling, origin history, review history, discovery history, or other non-normative narrative content.
* **[AG-DOC-003]** Area-specific `AGENTS.md` files, including `.github/AGENTS.md`, MUST take precedence over general repository rules within their explicitly stated scope.
* **[AG-DOC-004]** Architecture, release, threat-model, and other explicitly authoritative technical documentation MUST govern its stated system-design or procedure scope unless a higher-precedence applicable source conflicts.
* **[AG-DOC-005]** `README.md` and other user-facing documentation MUST have the lowest precedence among the documentation sources defined by `[AG-DOC-004]` through `[AG-DOC-007]`.
* **[AG-DOC-006]** Conflicting applicable requirements or interpretations MUST NOT be resolved by silently choosing one. Affected work MUST stop until the conflict is resolved.
* **[AG-DOC-007]** A conflict that cannot be resolved from verified source precedence and behavior MUST be escalated to the maintainer. The escalation MUST identify the conflicting sources and verified behavior. Recording the conflict without obtaining the required decision MUST NOT resolve it.
* **[AG-DOC-008]** Every exception to a hard rule MUST define `Scope`, `Reason`, `Tracking`, `Validation`, and `Non-Expansion`. An exception MUST be narrowly scoped and MUST NOT weaken requirements outside that explicit scope.

## AG-GH
* **[AG-GH-001]** All GitHub-visible content, including issues, pull request bodies, comments, automated review output, commit messages, code, code comments, and documentation, MUST be written in English regardless of producer. This rule MUST take precedence over `[AG-CC-002]`, `[AG-CC-003]`, and `[AG-CC-004]` for GitHub-bound content.
* **[AG-GH-002]** Issue bodies MUST include correct links to known related pull requests, issues, or parent tracking items.
* **[AG-GH-003]** Pull requests MUST reference their tracking issue in the pull request body whenever one exists.
* **[AG-GH-004]** Closing keywords such as `Fixes #123` or `Closes #123` MUST be used only when merging the pull request is intended to close that issue.
* **[AG-GH-005]** Non-closing references such as `Refs #123` MUST be used for parent trackers, design discussions, drafts, partial work, or other relationships that MUST remain open.
* **[AG-GH-006]** Known issue or pull request relationships MUST NOT exist only in chat history and MUST be persisted in GitHub.
* **[AG-GH-007]** Issues SHOULD carry labels, an issue Type, an applicable Milestone, Project-board assignment, and GitHub's native parent/sub-issue relationship when genuinely subordinate. An issue lacking applicable metadata SHOULD NOT be treated as fully triaged.
* **[AG-GH-008]** Every pull request body MUST include what changed, user-visible impact, validation performed, known risk, and follow-up work. A pull request missing this information MUST NOT be considered integration-ready.
* **[AG-GH-009]** Scaffold or partial-fix pull requests MUST identify themselves as scaffold or partial, MUST reference remaining scope with `Refs #N`, and MUST NOT use closing keywords for unresolved remainder.
* **[AG-GH-010]** After a pull request lands, completion MUST be checked against the merge commit or current `master` state and the original issue. Pull-request-head state alone MUST NOT establish completion.
* **[AG-GH-011]** Every issue MUST be independently actionable from its body alone. It MUST identify affected files, functions, or paths, define concrete verifiable acceptance criteria, and provide evidence through reproduction, logs, code references, or equivalent proof. An incomplete issue MUST be expanded before assignment.
* **[AG-GH-012]** A successor or follow-up issue MUST state whether it covers all original acceptance criteria or only a subset. A subset successor MUST identify the remaining criteria, and the original issue body MUST link the successor and MUST record that the original issue MUST NOT be closed until all remaining acceptance criteria are satisfied. Titles, labels, comments, or implied scope MUST NOT substitute for this status.
* **[AG-GH-013]** Before an issue is closed as resolved, superseded, or duplicate, its complete acceptance criteria MUST be compared with the covering pull request, issue, and current repository state. Topic, title, or scope similarity MUST NOT establish equivalence. An issue MUST NOT be closed unless all applicable acceptance criteria are satisfied or explicitly preserved as unresolved scope.
* **[AG-GH-014]** Before acting on, summarizing, reporting, closing, or determining scope or status of any issue or pull request, the complete title, body, and comment history MUST be read in chronological order. The body alone, latest comment, or dispatcher summary MUST NOT be sufficient. Large histories MAY be processed in complete consecutive chunks. Later comments MUST govern points they change, supersede, narrow, expand, or contradict. Stale body information MUST be corrected.

## AG-WF
* **[AG-WF-001]** Before starting or continuing branch work, or making readiness, mergeability, or integration-order claims, current remote branch and base MUST be fetched, the working branch MUST be rebased onto the current remote base, and resulting head MUST be verified. This MUST be repeated after restart or continuation and whenever freshness is uncertain. A failed rebase MUST block readiness, mergeability, or integration-order conclusions.
* **[AG-WF-002]** Direct pushes to `master` MUST be DISACK by default and MUST NOT occur without the exact maintainer phrase `ACK for merge to master`. All changes MUST be integrated into `master` through a pull request. Authorization MUST satisfy `[AG-WF-029]`.
* **[AG-WF-003]** Repository work MUST NOT be merged, closed, or deleted without explicit maintainer authorization satisfying `[AG-WF-029]`. Merge additionally MUST require the exact phrase `ACK for merge`.
* **[AG-WF-004]** A pull request MUST remain Draft until all required validation passes, all known review findings are resolved, and the complete change passes `[AG-LAW-001]`. Any unresolved validation failure, finding, or applicable rule violation MUST block Ready status.
* **[AG-WF-005]** A review thread MUST NOT be resolved until the finding satisfies `[AG-WF-011]` and is fully corrected or has a maintainer-approved explanation. Every fixed finding MUST then satisfy `[AG-WF-008]`.
* **[AG-WF-006]** Every fixed review finding MUST receive a factual reply describing the correction and MUST then be resolved through GitHub's `resolveReviewThread`. An outdated thread MUST still be explicitly resolved. Resolution MUST NOT delete thread content.
* **[AG-WF-007]** If GitHub does not permit resolution of a stale or outdated thread, a factual pull request comment MUST identify the finding, explain why it is fixed, and state that GitHub prevented thread resolution.
* **[AG-WF-008]** Before changing, reviewing, or resolving an issue or pull request, `[AG-GH-019]` MUST be satisfied and the surrounding file and project-wide impact MUST be evaluated. Every identified problem MUST be processed under `[AG-WF-011]`.
* **[AG-WF-009]** Every defect, review finding, or comparable failure MUST be treated as a failure class rather than an isolated instance. The root cause MUST be identified before the finding is considered fixed. The complete affected scope MUST be searched for other occurrences and consequences, including matching install, update, secondary, release, CI, documentation, and test paths where applicable.  A correction MUST eliminate the root cause across that affected scope and MUST NOT be limited to the reported line, file, symptom, example, or occurrence. If a behavior change or bug fix would also be required elsewhere to keep another implementation correct, that other implementation MUST be considered part of the same failure class.  Evidence required to claim a root cause MUST satisfy `[AG-INT-001]`.
* **[AG-WF-010]** Every change MUST be evaluated in its complete affected context, including dependencies, impact, resulting behavior, and foreseeable consequences. The entire affected file MUST be the minimum correctness unit. Directly connected inconsistencies or applicable violations MUST be corrected before completion, and the resulting change MUST pass `[AG-LAW-001]`.
* **[AG-WF-011]** `AGENTS.md` content, including rules, values, requirements, exceptions, and governed information, MUST NOT be silently removed, narrowed, simplified, or changed in representation or meaning without explicit maintainer consent. Modifications MUST preserve complete semantic content unless a meaning or scope change is explicitly authorized and MUST pass `[AG-LAW-001]`. Rule IDs MUST identify exactly one rule and MUST NOT be silently reused. References MUST follow `[AG-LAW-004]`.
* **[AG-WF-012]** New issue creation MUST be DISACK by default. Before creation, all issues including closed issues MUST be searched for identical or materially overlapping scope. Existing coverage MUST be reused. Uncertainty about coverage, ownership, scope, or need MUST stop creation and MUST be escalated through the coordinator to the maintainer when unresolved. Creation authorization MUST satisfy `[AG-WF-029]`.
* **[AG-WF-013]** Subagent results MUST be treated as stale until verified against the current remote base and pull request head. Before such results are used for readiness, conflict resolution, review comments, or merge guidance, reported commit and base MUST be compared with current GitHub state and applicable checks MUST be rerun against the current head.
* **[AG-WF-014]** Agents and tools MUST make technically determinable decisions independently. Guidance MUST be requested only when a choice has real operational impact involving hardware, network topology, cost, services, availability, or time-to-value. Technically determinable consequences MUST NOT be delegated back to the maintainer as preference questions. Source conflicts MUST follow `[AG-DOC-008]` through `[AG-DOC-010]`.
* **[AG-WF-015]** A second occurrence of the same underlying failure pattern MUST trigger assessment for a new or strengthened `AGENTS.md` rule and MUST NOT be handled only by fixing the repeated instance. Recurrence MUST be determined by underlying cause, not symptom.   Before proposing or assigning a new rule ID, the complete existing rulebook MUST be searched for a rule that already governs, overlaps with, or can canonically own the failure class. If an existing rule covers the failure class or can be strengthened without creating unrelated scope or ambiguity, that rule MUST be strengthened and a new rule ID MUST NOT be created. If multiple rules contain overlapping requirements for the same failure class, the overlap MUST be consolidated into one canonical owner while every unique requirement remains preserved. A new rule ID MAY be proposed only for a genuinely distinct invariant that cannot be incorporated into an existing rule without unrelated scope or ambiguity. The proposal MUST identify the existing rules checked, MUST explain why strengthening or consolidation is insufficient when a new ID is proposed, and MUST be presented to the maintainer with canonical English text and a German translation before adoption.
* **[AG-WF-016]** This rule MUST be the canonical durable-persistence contract. `Substantive knowledge` MUST include material findings, verified facts, evidence, reproductions, decisions, rejected alternatives and rationale, assumptions, constraints, limitations, unresolved questions, acceptance criteria, dependencies, risks, rollback information, implementation state, and required follow-up. A `durable record` MUST be a surviving repository or GitHub record that remains independently understandable without access to the originating chat, session, temporary environment, or worktree. Before an issue, pull request, branch, review thread, investigation, agent task, worktree, or comparable source is closed, merged, resolved, superseded, abandoned, deleted, cleaned up, handed off, or otherwise ended, all substantive knowledge not already present in the surviving durable record MUST be consolidated there. A link to a transient source MUST NOT count as consolidation. Chats, agent reports, local notes, temporary files, CI output, unpushed commits, branches, worktrees, or review discussions MUST NOT remain the only copy of substantive knowledge. Consolidation MUST preserve provenance, accepted and rejected decisions, current implementation state, and unresolved remainder. Summaries MAY be used only when all material conclusions, constraints, rationale, risks, rejected alternatives, and follow-up remain preserved. Significant state MUST be persisted during work and MUST NOT be deferred until final cleanup. Before an agent ends, hands off, removes its worktree, or allows its environment to terminate, substantive local work MUST be committed where appropriate, pushed to a named remote branch, and linked or summarized in a durable tracking object. Durable persistence MUST be verified before the lifecycle action through successful readback, expected commit and remote-branch verification, or equivalent proof. If transfer cannot be completed and verified, the source MUST remain active and completion or handoff MUST NOT be declared.
* **[AG-WF-017]** Every real defect, gap, missed edge case, inconsistency, or other problem found during work MUST be fixed in the same pass regardless of original scope or discovery path. A known problem MUST NOT be ignored, deferred, scoped out, or only recorded as a limitation, review finding, issue, or future task.  If resolution requires a maintainer decision or separate authorization, materially changes intended behavior, creates significant new risk, or causes another problem that cannot safely be resolved, affected work MUST stop and the maintainer MUST be contacted with the problem, impact, required decision, and available choices. The problem MAY remain unresolved only until that decision. 
* **[AG-WF-018]** This rule MUST be the canonical maintainer-authorization contract. A request for an opinion, preference, recommendation, or analysis MUST NOT authorize execution. When a rule requires maintainer authorization, authorization MUST come directly from the maintainer, MUST apply only to the specific action for which it was requested, and MUST NOT be inferred, substituted, reused, generalized, delegated, or transferred. Unless a more specific rule requires an exact phrase, authorization MUST use the literal token `ACK`. `DISACK` MUST prohibit the action. Tone, enthusiasm, implication, silence, elapsed time, contextual consent, or absence of objection MUST NOT substitute. When a specific rule defines an exact authorization phrase, that phrase MUST override generic `ACK` and MUST be matched exactly. If authorization is unclear, the intended action MUST be stated and explicit authorization MUST be obtained before execution.  A required maintainer decision MUST be recorded on the relevant GitHub issue or pull request as a structured statement identifying the exact decision and concrete options.
* **[AG-WF-019]** Documentation MUST NOT be treated as authoritative when it conflicts with verified code, architecture, or governance. Such conflicts MUST be handled under `[AG-DOC-002]` through `[AG-DOC-010]`.
* **[AG-WF-020]** A cohesive unit of work MUST NOT be split across multiple pull requests using only copied snapshots or prose merge-order instructions. Related pull request dependencies MUST be mechanically enforced through actual branch or rebase relationships, Draft state, disabled auto-merge, or equivalent controls. If mechanical enforcement is genuinely unavailable, the dependency MUST also appear prominently in title and body. Downstream work MUST NOT merge before required upstream dependencies.
* **[AG-WF-021]** A pull request MUST remain Draft while content is changing, findings are being fixed, commits are being pushed, or additional validation is running. It MAY become Ready only for a deliberate review pass and only when `[AG-WF-006]` permits.  After that review pass produces at least one review comment or a no-findings acknowledgment, the pull request MUST return to Draft before any further push, test-related change, or iteration. WIP pushes MUST NOT intentionally consume additional automated review runs.
* **[AG-WF-022]** A maintainer pause or stop instruction MUST remain in force until the maintainer supplies the exact phrase `ACK for continuation`, satisfying `[AG-WF-029]`. Pause state MUST propagate consistently across the complete dispatch hierarchy. No other party MAY override or reinterpret it.   A paused agent receiving a continue instruction from another party MUST refuse it and MUST state that the maintainer pause remains active.  A pause MUST NOT be treated as termination. Paused context or work MUST NOT be killed, discarded, or cleaned up without separate authorization.
* **[AG-WF-023]** Any administrative bypass, including `--admin` or another mechanism bypassing branch protection, required checks, reviews, or repository safeguards, MUST be DISACK by default and MUST require exact maintainer authorization `ACK for gh admin` under `[AG-WF-029]`.   Before authorization is requested, the root cause of every technically diagnosable blocker MUST be determined. The request MUST be one precise question identifying the pull request, exact protection or check to bypass, reason, and whether root cause was established.   Any unrelated output, action, event, or intervening communication between request and response MUST invalidate the request and MUST require a fresh one. Before any merge, whether normal or administratively bypassed, current remote state MUST be fetched, the pull request branch MUST be rebased onto its current base, and the resulting head and branch relationship MUST be verified. A stale, unrebased, or unverified branch MUST NOT be merged. Administrative authorization MUST NOT bypass rebasing, root-cause analysis, branch verification, review resolution, or another requirement unless that exact bypass was explicitly authorized.
* **[AG-WF-024]** Every nontrivial completed task MUST include a closing report containing all of the following:  `Context read`: every relevant issue, pull request, design document, code area, threat model, governance source, or other source actually read.  `Changed scope`: exact modified files, paths, components, or subsystems. `Deliberate exclusions`: related areas intentionally left unchanged and the reason.  `Validation`: every command actually executed, its exit status, material observed result, and every applicable check not executed with its reason.  `Documentation`: documentation checked under `[AG-DOC-001]`, updates made, and any remaining drift.  `Risks and open work`: known risk, partial implementation, dependency, limitation, exception, or pending verification.  `Follow-up`: every required issue, pull request, dependency, or task, or the exact statement `no follow-up required`. The report MUST satisfy `[AG-INT-001]`, `[AG-INT-002]`, and `[AG-WF-026]`. Generic, assumed, placeholder, or materially incomplete reporting MUST NOT satisfy this rule.
* **[AG-WF-025]** Opening a pull request by any means MUST be DISACK by default and MUST require the exact maintainer phrase `ACK for PR` under `[AG-WF-029]`. Branch work and pushing MAY proceed without it; pull request creation MUST NOT.
* **[AG-WF-026]** A single file read MUST NOT exceed 25000 tokens any Larger files MUST be read sequentially in chunks until the complete file has been read. Partial or truncated reads MUST NOT count as complete.  

## AG-INT
* **[AG-INT-001]** Every factual claim about code, repository state, files, configuration, commands, syntax, APIs, tools, tests, builds, runtime behavior, dependencies, environments, infrastructure, or external systems MUST be supported by evidence actually obtained during the current investigation. Lying, hallucinating, inventing, fabricating, or overstating information MUST NOT occur. Claim scope MUST NOT exceed evidence scope. Observed fact, static inference, hypothesis, expectation, and unverified assumption MUST remain distinct. Memory, plausibility, convention, documentation, comments, names, prior incidents, another agent's unsupported assertion, surrounding code, or absence of visible failure MUST NOT substitute for current evidence. Static evidence MUST support only static conclusions. Reading code MUST NOT prove runtime behavior. Reading a test MUST NOT prove that it passes. Documentation MUST NOT prove implementation behavior. One execution MUST prove only that execution under its actual conditions. Negative claims such as no duplicates, references, callers, failures, regressions, or impossibility MUST require an appropriately scoped search or equivalent evidence.   Current state MUST be rechecked when available. After implementation changes, relevant source MUST be reread and applicable verification MUST be executed before claims such as `VERIFIED`, `CONFIRMED`, `PROVEN`, `WORKS`, `FIXED`, `PASSES`, `SAFE`, `UNUSED`, or equivalent certainty are made. A suspected defect MUST NOT be called confirmed from a suspicious line alone. Confirmation MUST establish relevant reachability and material effect, MUST inspect applicable callers, guards, configuration, defaults, error handling, alternate paths, and compensating behavior, and MUST use empirical reproduction wherever technically feasible. Root cause MUST NOT be claimed unless evidence establishes it. If feasible reproduction was not performed, the defect MUST remain suspected or statically indicated. If reproduction is genuinely impossible, the limiting condition MUST be stated. Commands, outputs, tests, file contents, citations, paths, issue or pull request numbers, commits, versions, configuration values, capabilities, or completed actions MUST NOT be fabricated. Prepared, requested, initiated, or expected actions MUST NOT be reported as completed until their result is observed. `UNKNOWN` MUST remain `UNKNOWN` until verified. Direct evidence SHOULD be preferred whenever feasible.
* **[AG-INT-002]** Validation results MUST represent observed reality. Existing adverse evidence MUST NOT be hidden, suppressed, filtered, downgraded, masked, discarded, truncated, reclassified, excluded from scope, or converted into success while the underlying condition remains. Every wrapper, pipeline, helper, script, test runner, CI step, aggregator, and reporting layer MUST preserve the semantic result and relevant raw evidence of operations it invokes. A failure MUST propagate unless an independently justified semantic operation establishes that it is not a failure. Multiple independent findings MUST remain visible unless fail-fast behavior is explicitly part of intended semantics. Retries MUST preserve that retries occurred and MUST expose material failed-attempt evidence. Later success MUST NOT be reported as if the initial attempt succeeded. Flakiness MUST be treated as a defect and MUST NOT be hidden through retry-until-green behavior. A check MUST NOT be weakened because it is strict, noisy, inconvenient, preexisting, unrelated, environmental, difficult to fix, or currently failing. Validation scope, thresholds, severity, classification, applicability boundaries, exclusions, allowlists, suppression, or equivalent mechanisms MUST NOT be changed merely to obtain success. A legitimate skip MUST require an explicit testable inapplicability condition, MUST avoid executing the inapplicable target, MUST report `SKIP` or `NOT-RUN` rather than `PASS`, MUST state the reason, and MUST automatically reactivate when applicable. Before a validation mechanism is changed, the detected condition and signal cause MUST be established. The changed mechanism MUST be proven by a valid case that passes and an invalid case that still fails. After validation or reporting logic changes, the complete relevant result-propagation path MUST be verified. A detected adverse condition MAY only be resolved by fixing the underlying condition, fixing a demonstrably incorrect check, explicitly skipping a genuinely inapplicable check, or reporting the failure. A failing underlying condition MUST NOT produce `PASS`.

## AG-CODE
* **[AG-CODE-001]** Placeholder or scaffold markers such as `TODO(#123)` MUST be removed when their referenced work is implemented. Before completion, the affected scope MUST be searched for the replaced marker.
* **[AG-CODE-002]** Before implementing or modifying any capability, the complete relevant repository scope and applicable native capabilities MUST be searched for existing same or closely related behavior. Implementation MUST NOT begin before this search. Existing capabilities MUST be reused or extended when they already satisfy or can reasonably satisfy the requirement. Equivalent logic MUST NOT be reimplemented under another name, location, representation, or abstraction merely for convenience. Trivial size MUST NOT create an exemption. The search result MUST be recorded in the applicable Issue or PR using the following canonical confirmation:  `I confirm I did not violate AG-CODE-011 - I searched for <what was searched> and found no existing <function/helper/check/variable/mechanism> already doing <the job>, so I am implementing/modifying <what, and where>.`   If a duplicate is found, it MUST NOT be silently ignored. Implementations MUST share a mechanism whenever a bug fix or behavior change to one copy would also need to apply to another copy to keep both correct. Superficially similar but intentionally independent behavior MAY remain separate. Uncertainty about correct reuse, consolidation, or ownership MUST stop affected modification and MUST be escalated before work proceeds.
* **[AG-CODE-003]** `NEW FILE = DISACK` MUST be the default. Before creating any new implementation file, the relevant directory and implementation area MUST be searched for an existing owner of the same conceptual capability or lifecycle. The agent MUST determine whether existing files can own the behavior through functions, options, flags, subcommands, case dispatch, reusable helpers, additional tests, or equivalent native mechanisms. Existing sibling implementations MUST be checked for consolidation before another sibling is created. Duplicated or near-duplicated setup, validation, cleanup, parsing, resource discovery, logging, error handling, comments, or control flow MUST be treated as evidence for shared implementation or consolidation. Files SHOULD be treated as consolidation candidates when they operate on the same resource or lifecycle and differ primarily by execution mode, policy, safety level, filtering, environment, target, workflow phase, or small control-flow variations. The existing file whose established responsibility already covers or most closely owns the capability MUST be extended. Shared behavior MUST be implemented once. A fragmented family of near-identical files MUST NOT justify another sibling. A new file MUST NOT be created: because creation is easier than understanding an existing implementation; merely because behavior has a distinct name; by copying and modifying an existing file into another mode or phase; by moving file sprawl into another directory; by creating one file per helper unless the native format requires it; before approval and justified afterward. Consolidation MUST apply only to the same conceptual capability and MUST NOT force unrelated responsibilities into a god-file. Native composition models that structurally require separate units MAY retain those units. Open issues and pull requests MUST be checked for other consumers of the same capability, and the search and consolidation result MUST be recorded in the implementation record or pull request. If uncertainty remains about ownership, consolidation, or whether a new file is justified, DISACK MUST remain in force. A new file MAY be created only after the documented search establishes that no suitable existing home exists and explicit maintainer or coordinator ACK is obtained before creation.

## AG-VAL
* **[AG-VAL-001]** Repository warnings MUST be treated as errors except where an explicit rule defines a narrower exception. A check that emitted an applicable warning, failed setup, or used a broken fallback MUST NOT be reported as successful.
* **[AG-VAL-002]** `command not found`, missing files, missing required environment variables, permission errors, malformed commands, empty required outputs, failed tool setup, and equivalent standard failures MUST be hard failures.
* **[AG-VAL-003]** Required command failures MUST NOT be hidden with `|| true` or equivalent suppression. Optional fallback MAY be used only when the command is genuinely optional and the reason is documented. `[AG-INT-002]` MUST remain the governing evidence-integrity contract.
* **[AG-VAL-004]** Native local commands MUST be preferred when they can perform the same operation as a remote API. APIs MAY be used when no equivalent local operation exists or when required state exists only remotely.
* **[AG-VAL-005]** The narrowest relevant checks for changed files MUST be run, and every applicable check that cannot be run MUST be reported.
* **[AG-VAL-006]** Workflow changes MUST receive syntax validation and review of runner labels, secrets, variables, matrix behavior, and cache behavior.
* **[AG-VAL-007]** Validation MUST NOT be weakened to make a branch pass. An incorrect check MUST be replaced by an equally strong or stronger check validating intended behavior. `[AG-INT-002]` MUST govern any change to validation semantics.
* **[AG-VAL-008]** RTFM MUST be performed before assumptions about a third-party tool, image, dependency, API, or integration. Relevant behavior, configuration, limits, supported operations, and syntax MUST be verified against authoritative upstream documentation before design, change, weakening, documentation, or reporting based on that behavior. Memory, prior experience, observed defaults, inference, or undocumented behavior MUST NOT be treated as fact. Technical conclusions MUST use verifiable evidence. Missing or contradictory authoritative evidence MUST remain unverified.
* **[AG-VAL-009]** Blocking CI gates MUST NOT trust mutable external state as current. Every blocking check MUST resolve relevant dependencies to exact immutable state and MUST refresh them immediately before use when freshness affects correctness. Earlier steps, cached layers, or mutable references MUST NOT prove intended state.
* **[AG-VAL-010]** Before authoring a heuristic matcher against an external format or language syntax, the authoritative grammar MUST be read. Initial implementation MUST cover all documented relevant variations and MUST NOT be based only on the current example. `[AG-WF-011]` MUST separately govern failure-class handling after a finding exists.

## AG-SEC
* **[AG-SEC-001]** Known placeholders such as `CHANGE_ME_*` MUST NOT be valid runtime values and MUST be replaced or rejected before dependent services start.
* **[AG-SEC-002]** Private credentials, tokens, personal contact data, and internal LAN-only secrets MUST NOT be committed.
* **[AG-SEC-003]** GitHub Secrets MUST be used for secret values and GitHub Variables MUST be used for non-secret repository configuration unless a more specific rule requires another protected transport.
* **[AG-SEC-004]** If sensitive data appears in a branch, normal work MUST stop and the sensitive data MUST be removed from the active branch before work continues.

## AG-OP
* **[AG-OP-001]** Setup, update, and migration logic MUST be idempotent. Repeated execution with identical stable input MUST NOT rotate stable secrets, overwrite preserved configuration, or create new side effects. Stable output MUST remain byte-identical except for explicitly documented volatile fields. Stable secrets or tokens MUST NOT rotate on repeat execution; only missing values or known placeholders MAY be generated or regenerated.
* **[AG-OP-002]** Setup, update, and migration logic MUST converge old or incomplete installations toward current expected state. Already-converged state MUST be detected and MUST NOT be unnecessarily remutated.
* **[AG-OP-003]** Missing required configuration values SHOULD be generated when safe and MUST be rejected with a clear fail-closed error when user input is required.
* **[AG-OP-004]** Existing non-empty local values MUST be preserved by default.
* **[AG-OP-005]** Validation MUST occur before restart, pull, reload, or runtime mutation when failure could leave installation state worse. Failed validation MUST NOT leave the target half-written, proceed with mutation, or delete last-known-good state.
